## Active Requirements (v1.1)

### Authentication & Persistence (AUTH)
- [ ] **AUTH-01**: Upon receiving credentials from Vault, Sentinel persists exactly two files to disk: the CA certificate and the mTLS public certificate.
- [ ] **AUTH-02**: Sentinel retains the mTLS private key strictly in memory (e.g., variables, memfd) and ensures it never touches the local disk.
- [ ] **AUTH-03**: On startup, if no join token is provided (e.g., during an automatic restart), Sentinel checks the disk for the mTLS public cert to re-authenticate and request a completely new set of credentials (new public cert and new memory-only private key).

### Service & Resilience (SRV)
- [ ] **SRV-01**: Sentinel runs natively as a `systemd` service configured to automatically start on boot and automatically recover from crashes.
- [ ] **SRV-02**: The `systemd` unit configuration utilizes basic sandboxing (e.g., `ProtectSystem`) to further restrict access to the disk.

### Vault Integration & Polling (VAULT)
- [ ] **VAULT-01**: Vault (or the backend configuration) is configured to enforce an explicit downtime threshold (e.g., > 10 minutes), replying with a `403 Forbidden` or specific policy rejection if the threshold is exceeded.
- [ ] **VAULT-02**: Upon receiving a downtime block from Vault, Sentinel enters a "Wait-For-Approval" state and begins an exponential backoff polling loop instead of crashing and relying on `systemd` to retry infinitely.
- [ ] **VAULT-03**: When manual approval is granted on the backend (unlocking the block), Sentinel's next internal poll succeeds, it fetches the new credentials, and immediately resumes normal telemetry operations.
